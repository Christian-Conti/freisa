# 9. Real designs: any repository, as it is

The examples (blinky, uart_loopback) are plain RTL in this repository. A real design usually lives in its own repository
and comes with its own generators (scripts or python freisa.py targets that write part of the RTL or the file list) and often a
FuseSoC `.core` that lists files, dependencies, defines and per-board targets.

FREISA takes such a repository **as it is**: nothing is copied into FREISA and nothing in the repository changes. One
project file, `designs/<name>.yml`, says how to prepare the repository, where its file list is and which tool runs each
step.

## From the repository to the sources
| Key | What it does |
|-----|--------------|
| `repo` | the repository folder; every other path is relative to it |
| `prepare` | commands run in the repository before the sources are read, e.g. `make generate`. Each entry is a command, or `{run, cwd, conda, env}`: `conda` runs it in that conda environment (its tools, Python and `CONDA_DEFAULT_ENV`), `env` adds variables |
| `core`, `core_target` | the FuseSoC `.core` file and its target: FREISA runs `fusesoc run --setup` of that target in the build folder (FuseSoC resolves dependencies, generators and defines) and reads the file list it writes |
| `fusesoc` | `{conda, env, flags}`: where `fusesoc` runs, its extra variables, extra `fusesoc run` options |
| `edam` | instead of `core`: an EDAM file (`.eda.yml`) the repository already wrote; a glob picks the newest |
| `filelist` | instead of `core`: a `.f` / `.vc` file list |
| `exclude` | file patterns dropped from the list (e.g. a module defined twice) |
| `patches` | `[{file, from, to}]`: text replacements applied to copies of the files; the repository is untouched |
| `xdc` | pin and timing constraints |

From a FuseSoC file list FREISA takes the RTL in order, the include folders (the folder of each include file and the
`include/` folder above it) and the defines that have a value, as FuseSoC passes them. Xilinx primitives the RTL
instantiates (`IOBUF`, `BUFGCE`, ...) are known to the open synthesis.

A project lists its sources for the boards it supports, under `per_target`; on any other board `python freisa.py check` says so.

## Which flow
| Flow | Steps | When |
|------|-------|------|
| **Open** | `synth: yosys`, `place: dreamplacefpga`, `route: rwroute`, `bitgen: open_io` (UltraScale+), or everything `auto` (PYNQ-Z2) | RTL whose only I/O are pins and clocks: Vivado at most writes the bitstream file ([open_io](8-open-io.md)) |
| **Open synthesis** | `synth: yosys`, `netlist: vivado_link`, then `vivado` | RTL that instantiates I/O or clock primitives (I/O and clock buffers, clock managers), which the open placers cannot place |
| **Vivado** | every step `vivado` | the reference to compare the others with |

After `synth: vivado` the open placers cannot be used (the Vivado netlist has cells they do not know). `python freisa.py check` and
the interactive interface show such combinations before running, with the reason.

Designs that need Vivado IP generated by Tcl scripts (clock wizard, memory generator, block designs) are outside what
FREISA handles: their IP exist only inside a Vivado project. Designs with a Zynq PS block design have `bitgen: vivado_ps`
([Project files](3-projects.md)).

## Example
A system-on-chip whose repository generates its RTL with `make generate` (in a conda environment of its own) and
describes itself with a FuseSoC core that has one target per board:
```yaml
repo: ../../../my_soc                         # the repository, untouched
top: soc_fpga_top                             # its FPGA top

steps: {synth: yosys, netlist: vivado_link, place: vivado, route: vivado, bitgen: vivado, upload: openfpgaloader}

exclude: ["*/sim/*_clock_gate.sv"]            # a module the list defines twice
patches:                                      # SystemVerilog the open frontend rejects, fixed on a copy
  - {file: soc_fpga_top.sv, from: ".unused_io(1'b0),", to: ".unused_io(),"}

_common: &soc                                 # shared by every board (a YAML anchor)
  prepare:
    - {run: make generate, conda: my-soc-env}
  core: my_soc.core
  fusesoc: {conda: my-soc-env}

per_target:
  zcu104:
    <<: *soc
    core_target: zcu104
    xdc: [hw/constraints/zcu104_pins.xdc, hw/constraints/timing.xdc]
  pynq-z2:
    <<: *soc
    core_target: pynq-z2
    xdc: [hw/constraints/pynq-z2_pins.xdc, hw/constraints/timing.xdc]
```
`python freisa.py run -d my_soc -t zcu104` runs `make generate`, then `fusesoc run --setup` of target `zcu104` into
`build/my_soc/zcu104/fusesoc`, reads its file list, synthesizes with Yosys and has Vivado link, place, route and write
the bitstream; `python freisa.py upload` programs the board with openFPGALoader.

## Running several flows at once
Each run writes into `build/<design>/<board>`: runs of different designs or boards can go in parallel, one terminal
each. Two runs of the same design on the same board would write into the same folder. Several tools for one step in
parallel: `all` / `all_open` in `steps:` or `explore:` ([Using the flow](2-usage.md#several-runs-per-step-explore)).

## When it stops
The reason is printed at the end of the run and shown by the interactive interface; the log of the step is in the build
folder (`prepare_<n>.log`, `fusesoc_setup.log`, `synth.log`, `viv_*.log`, ...).
- **Unknown module**: a module missing from the file list (add it with `rtl:`).
- **Duplicate definition**: the list has two files for one module: drop one with `exclude:`.
- **SystemVerilog the open frontend rejects but Vivado accepts**: `patches:` on a copy, or `slang_args`.
- **A generator fails in `prepare` or `fusesoc`**: it is the repository's own tool; its log says what it needs (tools,
  variables: give them with `env:`).
